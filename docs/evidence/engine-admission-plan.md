# G5 调度与资源硬闸的后续实施分解（未实现）

冻结详设第一部分性能约束、册31调度/认领及并发隔离为依据。现有双进程 Redis/PG 观察通过只关闭观察路径，不能替代本计划。此文为实施分解，不变更原契约或冒称代码已经完成。

已实核问题：RunService.recover 每秒固定按 id 取前100个 RUNNING，并逐行新建虚拟线程；创建入口也直接启动线程，评测入口同步反复 drive。多次观察同一活跃运行没有本地调度去重，恢复队列无公平游标/调度时间，101号之后的旧运行可能长期得不到扫描。现节点租约 CAS 保证唯一逻辑提交，但不能当作线程/装配容量门禁。

## 实施顺序

1. **持久就绪队列及公平领取。** 保留 engine.run/node 为权威队列，按可执行节点与过期租约筛选，以短事务 SKIP LOCKED 领取调度机会并记录公平调度时间/代次。READY 依赖与WAITING_STEP/APPROVAL/EXTERNAL规则保持；不能只改SQL分页而声称资源并发完成。新建、恢复、确认续跑和外部事实就绪统一调度入口，跨副本不凭进程Map产生执行权。
2. **交互与批量分池。** CHAT/TASK/DEBUG 与 EVALUATION 的容量和队列各自有界；先取得本地执行槽再创建虚拟线程，重复本地run调度去重，finally释放。交互满载明确拒绝/提示 retryAfter；批量在PG排队，有界队列状态及可解释等待信息，不用内存无界队列。评测消费者相应处理受理/运行中/待确认，不能因改为异步就把 RUNNING 判失败。
3. **三类许可。** 模型、技能、上下文装配分别准入，释放与实际工作生命周期一致；多副本涉及外调配额的许可必须具备独立代次/租约和崩溃恢复，旧owner不能退掉新owner槽。不要在持PG行锁时等待资源或HTTP，不绕过现 ModelQuota/ToolCalls 的发送栅栏。
4. **六道内存闸补齐。** 大结果流式转存、事件PG有界读取、直接内存启动限制已有局部证据；历史与状态详情原文改为按需有界分页/投影，表达式不引入无界缓存且限制同时计算，线程/组装/缓存总预算封顶。响应超过边界有明确错误或摘要链接，不能悄悄截断事实。资源“计数字节”与真实JVM堆/直接内存曲线须分别记录。
5. **优雅停机。** 停止新认领，保留正在执行的租约续期至drain上限，超限由真实过期租约接管，旧代提交拒绝；不把 kill/停机等同外部副作用回滚。观察连接生命周期与业务任务生命周期继续分离。

## 必须保留的失败路径

- 前100个长期活跃时，后续就绪运行仍获执行机会；两域池满载互不挤占；反复recover不制造无界线程；过期、取消、拒绝与异常路径permit最终回收。
- 实际两个引擎同时领取、并发确认/恢复/取消，旧代晚到拒绝且外调计数不新增；批量排队重启可恢复，交互拒绝不留下伪成功或无法追踪的run。
- 模型/技能/装配任一饱和时其余域的健康/停止/状态查询仍可响应；取消等待槽的任务不会先外调再报告取消。
- 状态/历史/表达式/输出有大小或时间越界反例，真实慢写/断线仍持有必要permit，且不会以提前释放掩盖阻塞线程。
- 精确保留已有 output retry/计量、CALLBACK/UNKNOWN、两阶段发布/评测和CHAT历史授权规则的整轮回归。

容量验收另按原 T05/T33 使用固定资源运行500并发/5000 SSE/200×5MiB并收集曲线，不以可配置上限或fixture小样称目标通过。实现阶段应冻结相关源码、独立评审、再更新开发运行进程；未验收的生产IAM/容量门禁不因此开启。
